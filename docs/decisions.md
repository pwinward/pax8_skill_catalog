# Decision Log — Skills Catalog

Format mirrors PRD §12. The PRD's own decisions D1 (access is through an AI assistant), D2 (versioning is in the MVP) and D3 (authentication and de-duplication are out of scope) are inherited, not restated.

All decisions below: 2026-09-18, P Winward.

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| D-01 | The catalog is a shared service that assistants connect to, not a store embedded in each assistant | PRD §1's pain is that a skill "lives locally, on the author's own machine." A per-developer store passes every functional requirement while reproducing the problem | A catalog embedded in each developer's MCP server, sharing a database file. Workable, but "where does the catalog live?" answers as "a file on your laptop" |
| D-02 | One process: the MCP server *is* the catalog, over streamable HTTP | Fewest moving parts of any design that genuinely shares. The process outlives any assistant session, and one writer fronts the database | (a) stdio transport — a stdio server can only serve the client that spawned it and dies with the session. (b) A separate access tier forwarding to a catalog service — in production that tier is AgentCore Gateway, managed infrastructure we would not write, so building a local stand-in is less faithful, not more |
| D-03 | Python, official `mcp` SDK, managed with `uv` | The Bedrock agent ecosystem is Python-first. `uv` installs its own pinned Python, so the quickstart works regardless of the reviewer's OS or Python version — PRD §9 requires it to run on their machine, and we do not know what that machine is | Java/Spring (ceremony disproportionate to a single-module service), TypeScript (needs a Node install; SQLite needs a native dependency), the standalone `fastmcp` package (a superset we need nothing from, and it invites "why not the official SDK?") |
| D-04 | SQLite as the system of record, FTS5 for discovery | In the standard library, so the reviewer installs nothing. ACID transactions give PRD §7's atomicity outright, and FTS5 does the query-layer job inside the record store — no second system, no dual-write, no sync lag | Postgres (needs Docker or a local install, breaking the one-command quickstart), filesystem plus JSON (atomicity and search both hand-rolled), OpenSearch as the record store (a search index should never be the source of truth; it is a rebuildable projection) |
| D-05 | File bytes stored inline in SQLite | Filesystem writes do not join a SQL transaction. A crash between the two leaves orphaned files or rows pointing at nothing, which would need temp-write-and-rename plus an orphan sweep to approximate what one transaction gives | Content-addressed files on disk with metadata in SQLite |
| D-06 | No `latest_version` column; latest is derived with `MAX(version)` | A stored pointer is a second source of truth that can drift — an odd thing to carry in a system whose selling point is that nothing drifts. Deriving it is a reverse scan on an existing index | A denormalized pointer, which is more obvious to a reader |
| D-07 | A skill travels as a path-to-content map in both directions, with `SKILL.md` carried as a file | The catalog never composes or rewrites content, so retrieved bytes are identical to published bytes by construction rather than by care. PRD §4 itself calls the manifest "the file that carries a skill's name, description, and instruction body" | Taking `name`, `description` and `body` as arguments and rendering `SKILL.md` on retrieve. Simpler validation — missing fields are missing arguments — but the client reassembles the manifest, so two clients can write different bytes from one published version |
| D-08 | File contents must be UTF-8 text; binaries are rejected at publish | JSON strings cannot carry arbitrary bytes. Accepting binaries would force base64 on the way out — either everywhere (opaque, 33% larger) or per-file with an encoding flag — or a download URL, which is a different retrieve design | Base64 everything; a tar or zip upload endpoint |
| D-09 | Publish and retrieve both go through MCP tool arguments rather than a file upload endpoint | Symmetry is what makes the round-trip guarantee simple. A tar endpoint also brings archive extraction risks — path traversal in entries, decompression bombs, symlink escapes | A multipart or tar upload. Note PRD §7 requires only *discover and retrieve* to be assistant-mediated, so an upload endpoint would have been legal. The cost we accept instead: publishing spends tokens proportional to skill size, and executable bits do not survive |
| D-10 | Domain outcomes return as structured results; only genuine faults raise | "No" is an answer, not a failure. Marking it an error conflates a broken catalog with a working one reporting the truth, and leaves the log unable to tell them apart. A rejected publish carries no version number, so there is nothing to misreport as success | MCP's `isError` for not-found and validation failures — the spec-idiomatic choice for tool-level errors, and a reasonable alternative |
| D-11 | Re-publishing byte-identical content creates version N+1 | FR-04 says publishing under an existing name creates a new version, with no carve-out. De-duplication is out of scope per PRD §8 | Returning the existing version unchanged. `list_skill_versions` marks identical hashes instead, so the history stays honest without suppressing anything |
| D-12 | Flat global namespace keyed by skill name; publisher recorded but unverified | FR-04 keys versioning on name alone and PRD §8 removes authentication, so there is no identity available to disambiguate | Namespacing by publisher, which cannot be enforced without auth. Risk accepted and recorded: any caller may version anyone's skill |
| D-13 | Tests land with the code they cover | If tests were a final phase they would be the first thing cut at the four-hour mark, leaving a traceability table full of unbacked claims | Strict TDD (red-green churn on every unit); tests last |
| D-14 | Logging trimmed to tool name, outcome and duration, on stdout | The PRD never asks for logging, but cutting the latency test left Requirement 6 with no evidence. No timing assertion is made, because PRD §7 prescribes no threshold and a flaky test would encode one by accident. Stdout because telemetry should not live inside the system it observes | A richer event (argument shapes, result counts, agent handoffs, cost) — a Phase 2 item; a log table in the catalog database |
| D-15 | No Docker | The service is one process and one file. A container would add a volume-mounting failure mode to the very requirement (PRD §9) it would be meant to serve | Docker Compose, which only makes sense for the multi-process designs rejected in D-02 |
| D-16 | PRD §12's Q1 is answered in writing, not implemented | §11 scopes Phase 1 to FR-01 through FR-04 and describes Phase 2 as "left to be identified." Q1's owner is the builder, and the deliverable is a judgment | Building Phase 2 items, which would come out of Phase 1's quality |
